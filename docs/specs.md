# Спецификация учебного проекта: AI-разбор логистических жалоб

**Проект:** `delivery-claims-ai`
**Дата:** 2026-09-23
**Стек:** LangGraph (оркестрация графа агента) · LangSmith (трассировка, датасеты, оценка, мониторинг) · SQLite (локальная mock-БД заказов)
**Аудитория:** учебная — цель показать связку «граф состояний + инструменты + human-in-the-loop + наблюдаемость».

---

## 1. Бизнес-контекст и задача

### 1.1. Проблема
Интернет-магазин получает поток жалоб от клиентов на доставку. Значительная часть — жалобы на **опоздание** товара. Ручной разбор каждой жалобы дорог: оператор открывает CRM, ищет заказ, сверяет обещанный и фактический срок доставки, решает, правомочна ли жалоба, и назначает компенсацию.

### 1.2. Что делает система
AI-пайплайн автоматизирует **подготовку решения**, оставляя финальное слово за менеджером:

1. Принимает свободный текст жалобы от клиента.
2. **Классифицирует** жалобу (тип, тональность, срочность).
3. **Извлекает** идентификатор заказа и суть претензии.
4. **Обогащает** данными из БД: обещанный срок доставки vs. фактический.
5. Выносит **суждение о правомочности** жалобы (обоснована / не обоснована / недостаточно данных) — это делает **LLM-судья**, а не детерминированный алгоритм; с аргументацией и предложением по компенсации.
6. Передаёт результат на **ревью менеджеру** (human-in-the-loop): подтвердить / отклонить / скорректировать.
7. Фиксирует финальное решение и обратную связь менеджера.

### 1.3. Границы (scope)
- **В scope:** жалобы на срок доставки (опоздание). Только текстовый вход через **CLI** (§2.1). Один заказ на жалобу.
- **Вне scope:** жалобы на качество/комплектность товара, возвраты, multi-order жалобы, реальная интеграция с CRM/платёжкой, авторассылка ответов клиенту.
- **Учебное упрощение:** данные о заказах — локальная SQLite с заранее подготовленными записями.

### 1.4. Метрики успеха (учебные)
| Метрика | Определение | Цель |
|---|---|---|
| Точность классификации | доля верно определённых типов жалоб на тестовом наборе | ≥ 0.9 |
| Точность суждения о правомочности | совпадение вердикта модели с эталоном менеджера | ≥ 0.85 |
| Доля авто-подтверждений | % кейсов, где менеджер согласился без правок | наблюдаемая |
| Полнота извлечения order_id | % жалоб, где ID заказа найден корректно | ≥ 0.95 |

## 2. Общая архитектура

```
┌──────────────┐    текст жалобы     ┌───────────────────────────────────────┐
│   Клиент     │ ──────────────────▶ │           LangGraph-приложение         │
└──────────────┘                     │  (граф состояний claim-workflow)       │
                                     │                                        │
                       ┌─────────────┤  узлы: classify → extract → enrich →   │
                       │             │        judge → [interrupt] review →    │
                       │  tool-вызов │        finalize                        │
                       ▼             └───────────────┬────────────────────────┘
                ┌──────────────┐                     │  результат на ревью
                │  SQLite БД   │                     ▼
                │  (заказы,    │            ┌──────────────────┐
                │   доставки)  │            │  Менеджер (HITL) │
                └──────────────┘            └──────────────────┘
                       │                             │
                       └──────────── трассировка ────┴──────────┐
                                                                 ▼
                                                     ┌──────────────────────┐
                                                     │      LangSmith        │
                                                     │ traces · datasets ·   │
                                                     │ evaluators · monitor  │
                                                     └──────────────────────┘
```

**Ключевые компоненты:**
- **Граф LangGraph** — конечный автомат из узлов; между узлами передаётся общий объект состояния (`State`). Персистентность состояния через checkpointer (SQLite), что позволяет приостанавливать граф на этапе ревью и возобновлять после ответа менеджера.
- **Инструменты (tools)** — функции доступа к БД заказов (`get_order`, `get_delivery_facts`).
- **LLM** — модель-судья: классификация, извлечение, вынесение суждения (структурированный вывод).

> **Разделение ответственности (ключевой принцип проекта).**
> - **Код отвечает за истину о мире:** извлекает факты из БД и детерминированно вычисляет `delay_days`, `is_late`, статус, а также опорную шкалу компенсаций. Эти величины LLM **не пересчитывает и не переопределяет**.
> - **LLM отвечает за суждение:** обоснована ли жалоба, что предложить клиенту, стоит ли эскалировать — взвешивая факты, тон и контекст. Правила §6 для LLM — это **ориентиры (guidelines) внутри промпта**, а не жёсткий алгоритм; в спорных/пограничных случаях модель судит сама.
>
> Тем самым проект демонстрирует настоящую ценность LLM-as-judge (иначе оценщики и фидбэк менеджера в LangSmith были бы бессмысленны — оценивать было бы нечего).
- **Human-in-the-loop** — механизм `interrupt`: граф останавливается перед `finalize`, ждёт решения менеджера.
- **LangSmith** — сквозная наблюдаемость и оффлайн/онлайн-оценка качества.

### 2.1. Входной слой (CLI)

Вход в проект — **консольный**, никакого веб-UI/API (учебное упрощение; §1.3). Слой ввода тонкий и заменяемый: он лишь передаёт текст жалобы в граф и печатает результат.

- **Подача жалобы:**
  `python -m src.cli submit --text "..."` или `--file complaint.txt`. Команда создаёт `thread_id` (= id жалобы), запускает граф и выполняет его до `interrupt` перед ревью. В консоль печатается карточка для менеджера (§9) и `thread_id`.
- **Ревью менеджера:**
  `python -m src.cli review --thread <id> --decision approve|edit|reject [--verdict ... --action ... --comment "..."]`. Команда возобновляет граф с сохранённого состояния (checkpointer) и доводит его до `finalize`.
- **Демо-прогон:**
  `python -m src.cli demo` — гоняет заранее заготовленные кейсы из `claims_golden` (§8.3) насквозь, удобно для показа трасс в LangSmith.
- **Источник текста жалобы:** в учебном проекте это то, что вы ввели в `--text/--file`, либо фикстуры из датасета. Реальной интеграции с почтой/чатом нет (вне scope).

> Так как подача и ревью — **две отдельные CLI-команды, разнесённые во времени**, HITL-пауза графа на checkpointer видна буквально: между `submit` и `review` процесс может быть завершён, состояние переживает перезапуск.

### 2.2. Модели и провайдер (OpenRouter)

Все LLM-вызовы идут через **OpenRouter** (единый OpenAI-совместимый эндпоинт; в LangChain подключается как ChatOpenAI-совместимый клиент с `base_url` OpenRouter и ключом `OPENROUTER_API_KEY`). Это даёт один ключ на все модели и лёгкое переключение модели-судьи для сравнения версий в LangSmith.

**Модель на узел (конфигурируется, не захардкожено):**

| Узел | Роль | Класс модели | Почему |
|---|---|---|---|
| `classify` | классификация | быстрая/дешёвая | простая задача, важны скорость и цена |
| `extract` | извлечение order_id + суть | быстрая/дешёвая | структурный парсинг, не требует «ума» |
| `judge` | вынесение вердикта | сильная (reasoning) | ключевое суждение (вариант B) — качество важнее цены |
| evaluators (LLM-as-judge) | оффлайн-оценка §8.4 | сильная, **иная**, чем судья | независимый оценщик не должен совпадать с оцениваемой моделью |

**Дефолтный набор (бюджетный, редактируется в `.env`):**

| Переменная | Узел | Модель по умолчанию (OpenRouter slug) | Примечание |
|---|---|---|---|
| `MODEL_CLASSIFY` | `classify` | `google/gemini-2.5-flash-lite` | очень дёшево, быстрый, надёжный structured output |
| `MODEL_EXTRACT` | `extract` | `google/gemini-2.5-flash-lite` | та же модель — задача однотипная |
| `MODEL_JUDGE` | `judge` | `deepseek/deepseek-chat` (DeepSeek V3) | недорогой, но сильный в рассуждении — годится для варианта B |
| `MODEL_EVAL` | evaluators §8.4 | `openai/gpt-4o-mini` | иное семейство, чем судья, — независимая оценка; дёшево |

- Все четыре — из нижнего ценового сегмента; апгрейд судьи (напр. на `anthropic/claude-3.5-haiku` или более сильную reasoning-модель) — одна правка `MODEL_JUDGE` в `.env`, удобно сравнивать в LangSmith.
- Слаги и цены на OpenRouter меняются — **перед стартом сверьтесь с актуальным списком** и наличием у модели надёжного JSON/structured-mode (см. риск §12).
- Конкретные id моделей вынесены в **конфиг/`.env`**, чтобы менять модель без правки графа и прогонять A/B по судье.
- **Ключи и секреты:** `OPENROUTER_API_KEY`, `LANGSMITH_API_KEY`, `LANGSMITH_PROJECT` — только в `.env` (в `.gitignore`), не в коде.
- **Structured output:** на всех узлах — строгая JSON-схема; при подаче через OpenRouter выбирать модели с надёжной поддержкой structured/JSON-mode (кандидат-риск §12: у части моделей она слабее — предусмотреть валидацию и повтор).
- **Совместимость с LangSmith:** трассировка не зависит от провайдера — вызовы через OpenRouter логируются так же (токены/латентность/стоимость видны в трассах).

### 2.3. Технические решения

Зафиксированные до реализации решения. Сгруппированы: сначала три ключевых (влияют на архитектуру), затем принятые дефолты.

**Ключевые:**

1. **Structured output — JSON-mode + Pydantic-валидация + retry.**
   Не полагаемся на `with_structured_output()` (у части дешёвых OpenRouter-моделей он ненадёжен, §12). Вместо этого: запрашиваем JSON-mode, парсим в Pydantic-модель узла, при невалидном/неполном ответе — **один повтор** с уточняющей инструкцией; при повторной неудаче узел отдаёт безопасный дефолт (напр. `insufficient_data` для `judge`). Единый модуль схем на все узлы.

2. **Ветка `reject` менеджера — стоп с пометкой «на ручной разбор».**
   Отклонение завершает граф, кейс помечается для ручного разбора; автоматический повторный прогон `judge` **не делается**. Полноценный re-judge с учётом комментария менеджера (agentic-цикл с защитой от зацикливания) вынесен в «дальнейшее развитие» (§11).

3. **Фиксированная «дата прогона» для воспроизводимости.**
   Ветки суждения про `in_transit` зависят от «сегодня» (`today > promised_date`). Вводим конфиг-переменную **`RUN_DATE`** (по умолчанию — системная дата); в тестах и датасете `claims_golden` она фиксируется, чтобы эталонные вердикты были детерминированы независимо от дня прогона.

**Принятые дефолты:**

| Область | Решение |
|---|---|
| Язык/рантайм | Python 3.11+ |
| Менеджер зависимостей | **uv** |
| Checkpointer LangGraph | `SqliteSaver`, отдельный файл `data/checkpoints.db` (не смешивать с mock-БД заказов) |
| Датасет `claims_golden` | ~10–15 кейсов, покрывающих все ветки §6 (опоздание, в срок, `in_transit` ×2, `lost`, заказ не найден, нет order_id, пограничный) |
| Валидация вывода LLM | Pydantic-модели на каждый узел, единый модуль схем |
| Конфиг компенсаций | простой YAML/`.py`-словарь, подставляется в промпт `judge` как опорная шкала (§6) |

## 3. Модель данных (SQLite)

Учебная mock-БД. Файл: `data/orders.db`. Заполняется сид-скриптом фиксированными записями для воспроизводимости.

### 3.1. Таблица `orders`
| Поле | Тип | Описание |
|---|---|---|
| `order_id` | TEXT PK | Идентификатор заказа (напр. `ORD-10432`) |
| `customer_id` | TEXT | Идентификатор клиента |
| `created_at` | DATETIME | Дата оформления заказа |
| `carrier` | TEXT | Служба доставки |
| `sla_days` | INTEGER | Обещанный срок доставки в днях от `shipped_at` |

### 3.2. Таблица `deliveries`
| Поле | Тип | Описание |
|---|---|---|
| `order_id` | TEXT FK | Ссылка на `orders.order_id` |
| `promised_date` | DATE | **Обещанная** дата доставки (что видел клиент) |
| `shipped_at` | DATETIME | Фактическая дата отгрузки |
| `delivered_at` | DATETIME NULL | **Фактическая** дата доставки (NULL, если ещё не доставлен) |
| `status` | TEXT | `delivered` / `in_transit` / `lost` |

### 3.3. Производные величины (вычисляются, не хранятся)
- `delay_days = delivered_at − promised_date` (в днях; отрицательное = доставлено раньше срока).
- `is_late = delay_days > 0`.
- Для `in_transit`/`lost` — особые ветки суждения (см. §6).

### 3.4. Примеры сид-данных (для тестов и датасетов)
| order_id | promised_date | delivered_at | status | Ожидаемый вердикт |
|---|---|---|---|---|
| ORD-10432 | 2026-09-10 | 2026-09-14 | delivered | обоснована (опоздание 4 дня) |
| ORD-10510 | 2026-09-12 | 2026-09-11 | delivered | не обоснована (в срок) |
| ORD-10788 | 2026-09-15 | NULL | in_transit | недостаточно данных / ещё не доставлен |
| ORD-99999 | — | — | — | заказ не найден |

## 4. Состояние графа (`State`)

Единый типизированный объект, проходящий через все узлы. Поля накапливаются по мере выполнения.

| Поле | Тип | Заполняется в узле | Описание |
|---|---|---|---|
| `raw_complaint` | str | (вход) | Исходный текст жалобы |
| `channel` | str | (вход) | Канал (email/chat/form) — опц. |
| `category` | enum | classify | `delivery_delay` / `other` |
| `sentiment` | enum | classify | `negative` / `neutral` / `positive` |
| `urgency` | enum | classify | `low` / `medium` / `high` |
| `order_id` | str \| None | extract | Извлечённый ID заказа |
| `claim_summary` | str | extract | Нормализованная суть претензии |
| `order_facts` | dict \| None | enrich | Данные из БД: promised/delivered/status |
| `delay_days` | int \| None | enrich | Вычисленное опоздание |
| `verdict` | enum | judge | `justified` / `not_justified` / `insufficient_data` |
| `reasoning` | str | judge | Аргументация вердикта |
| `proposed_action` | dict | judge | Предложение (компенсация/отказ/эскалация) |
| `review_status` | enum \| None | review | `approved` / `rejected` / `edited` |
| `manager_feedback` | dict \| None | review | Правки и комментарий менеджера |
| `final_decision` | dict | finalize | Итоговое решение |

## 5. Граф LangGraph: узлы и рёбра

### 5.1. Диаграмма потока

```

           │
           ▼
   ┌───────────────┐
   │ 1. classify   │  тип, тональность, срочность
   └───────┬───────┘
           │
     category == delivery_delay?
        ┌──┴───┐
      нет│     │да
         ▼     ▼
   ┌─────────┐ ┌───────────────┐
   │ route_  │ │ 2. extract    │  order_id + суть претензии
   │ other   │ └───────┬───────┘
   │ (END с  │         │
   │ пометкой│   order_id найден?
   │ «не в   │      ┌──┴───┐
   │ scope») │    нет│     │да
   └─────────┘       ▼     ▼
             ┌──────────────┐ ┌───────────────┐
             │ judge:       │ │ 3. enrich     │  tool → SQLite
             │ insufficient │ └───────┬───────┘  promised/delivered/delay
             │ _data        │         │
             └──────┬───────┘         ▼
                    │         ┌───────────────┐
                    │         │ 4. judge      │  вердикт + аргументация
                    │         └───────┬───────┘  + proposed_action
                    └────────┬────────┘
                             ▼
                    ┌───────────────────┐
                    │  ⏸ interrupt      │  ← human-in-the-loop
                    │  5. review        │     менеджер: approve/
                    └─────────┬─────────┘        reject/edit
                              │
                        review_status?
                     ┌────────┼─────────┐
              rejected│  edited│  approved│
                      ▼        ▼          ▼
                 (пересмотр  (применить  ┌──────────────┐
                  вердикта    правки →    │ 6. finalize  │
                  или END)    finalize)   └──────┬───────┘
                                                 ▼
                                              (END)
```

### 5.2. Описание узлов

**1. `classify`**
Вход: `raw_complaint`. LLM со структурированным выводом определяет `category`, `sentiment`, `urgency`. Условное ребро: если `category != delivery_delay` → узел `route_other` (вежливая пометка «жалоба не относится к срокам доставки», завершение). Иначе → `extract`.

**2. `extract`**
LLM извлекает `order_id` (по паттерну `ORD-\d+` и/или из контекста) и формирует `claim_summary`. Если ID не найден → сразу вердикт `insufficient_data` (пропуск enrich).

**3. `enrich`**
Вызывает инструменты БД:
- `get_order(order_id)` → метаданные заказа;
- `get_delivery_facts(order_id)` → `promised_date`, `delivered_at`, `status`.
Если заказ не найден → вердикт `insufficient_data`. **Детерминированно** (кодом, без LLM) вычисляет `delay_days`, `is_late`, определяет статус и опорный размер компенсации по шкале §6 — это факты, которые дальше LLM менять не вправе. Кладёт всё в `order_facts`.

**4. `judge` (LLM судит фактически)**
LLM-судья получает `claim_summary` + `order_facts` (обещанная/фактическая даты, `delay_days`, статус, опорная компенсация) и **самостоятельно выносит суждение**, а не сверяется с таблицей как код:
- `verdict`: обоснована / не обоснована / недостаточно данных;
- `reasoning`: аргументация со ссылкой на конкретные факты (даты, дни опоздания);
- `proposed_action`: тип и размер компенсации либо мотивированный отказ; эскалация.
Правила §6 передаются модели как **ориентиры**, а не как жёсткий алгоритм: в типовых случаях модель следует им, в спорных/пограничных решает по совокупности (тон обращения, контекст, здравый смысл).
Ограничения-инварианты: (1) **факты из БД приоритетнее утверждений клиента**; (2) модель **опирается только на переданные факты и не пересчитывает даты/дни/суммы** — арифметику уже сделал `enrich`; (3) при нехватке данных обязана вернуть `insufficient_data`.

**5. `review` (interrupt / human-in-the-loop)**
Перед этим узлом граф вызывает `interrupt` — исполнение приостанавливается, состояние сохраняется в checkpointer. Менеджеру показывается карточка: текст жалобы, факты из БД, вердикт модели, аргументация, предлагаемое действие, ссылка на трассу LangSmith. Менеджер:
- **approve** → `finalize` с решением модели;
- **edit** → менеджер меняет вердикт/действие, правки идут в `manager_feedback` → `finalize`;
- **reject** → решение отклонено; учебная ветка: завершение с пометкой «на ручной разбор» (в проде — возврат на `judge` с доп. инструкцией).
После ответа граф возобновляется с сохранённого состояния.

**6. `finalize`**
Формирует `final_decision`, логирует итог, отправляет `manager_feedback` в LangSmith как обратную связь на соответствующую трассу (ground truth для последующей оценки). Завершение.

### 5.3. Персистентность и возобновление
- **Checkpointer:** SQLite-сейвер LangGraph хранит снапшоты состояния по `thread_id` (= id жалобы).
- На `interrupt` состояние фиксируется; приложение может быть перезапущено, ревью — прийти минуты/часы спустя. Возобновление — по `thread_id` с командой продолжения, содержащей решение менеджера.

## 6. Логика суждения: ориентиры для LLM (не жёсткий алгоритм)

> Важно: таблица ниже — это **guidelines в промпте узла `judge`**, а не код. LLM судит фактически (вариант B): в типовых ситуациях следует ориентирам, в спорных/пограничных выносит собственное суждение и обязан обосновать его фактами. Детерминированно кодом считаются только `delay_days`, `is_late`, статус и опорная компенсация (в `enrich`) — их LLM не переопределяет.

| Типовая ситуация | Факты (посчитаны кодом) | Ожидаемый ориентир | proposed_action (пример) |
|---|---|---|---|
| Опоздание подтверждено | `status=delivered`, `delay_days > 0` | скорее `justified` | компенсация по опорной шкале от `delay_days` |
| Доставлено в срок / раньше | `status=delivered`, `delay_days ≤ 0` | скорее `not_justified` | вежливый отказ с фактами |
| Ещё в пути, срок не наступил | `status=in_transit`, `today ≤ promised_date` | скорее `insufficient_data` | ожидание, повторная проверка |
| В пути, срок превышен | `status=in_transit`, `today > promised_date` | скорее `justified` | эскалация в службу доставки |
| Потерян | `status=lost` | скорее `justified` | полный возврат / переотправка |
| Заказ не найден / нет order_id | — | `insufficient_data` | запросить уточнение у клиента |

**Где LLM решает сам (ради этого и выбран вариант B):** пограничное опоздание в пределах погрешности; клиент указывает на важный контекст сверх формального SLA (обещанный подарок к дате, критичность); резко негативный тон при формально небольшом опоздании; несовпадение слов клиента с фактами. Здесь модель может отклониться от ориентира — но обязана объяснить почему, опираясь на факты.

**Опорная шкала компенсации (учебная):** 1–2 дня → извинение; 3–5 дней → промокод 10%; 6+ дней → промокод 20% + приоритетная доставка. Считается кодом в `enrich` и передаётся модели как **рекомендация**; LLM может предложить иное с обоснованием, но итог в любом случае проходит ревью менеджера (§9). Значения вынесены в конфиг.

## 7. Промпты (описание, без готового кода)

Для каждого LLM-узла — отдельный шаблон с чётким контрактом на структурированный вывод.

- **classify:** «Ты классификатор жалоб интернет-магазина. Верни category/sentiment/urgency строго из перечисленных значений. Не придумывай новые категории.»
- **extract:** «Извлеки идентификатор заказа (формат ORD-число) и одним-двумя предложениями сформулируй суть претензии. Если ID нет — верни null, ничего не выдумывай.»
- **judge (LLM судит фактически):** «Ты выносишь решение о правомочности жалобы на срок доставки. Тебе даны: суть претензии клиента и **посчитанные системой факты** (обещанная дата, фактическая дата, статус, дни опоздания `delay_days`, опорная компенсация). Ниже — ориентиры (см. §6), не жёсткие правила: в типовых случаях следуй им, в спорных/пограничных решай сам и объясняй почему. Инварианты: (1) факты приоритетнее слов клиента; (2) НЕ пересчитывай даты, дни и суммы — они уже посчитаны, используй как есть; (3) при нехватке данных верни insufficient_data. Верни verdict, reasoning (со ссылкой на конкретные факты и, если отклоняешься от ориентира, — с обоснованием), proposed_action.»

**Принципы:** структурированный вывод (JSON-схема) на каждом узле; запрет галлюцинаций фактов; явное разделение «слова клиента» и «данные системы»; версионирование промптов (в т.ч. через LangSmith Prompt Hub — опционально).

## 8. Наблюдаемость и оценка: LangSmith

### 8.0. Развёртывание: облачный LangSmith (SaaS, free tier)
- Используется **облачный** LangSmith на `smith.langchain.com` — никакой инфраструктуры не разворачиваем, только регистрация и `LANGSMITH_API_KEY`.
- Тариф — **бесплатный** (личный): лимита трасс с запасом хватает учебному проекту.
- Включение: переменные окружения в `.env` — `LANGSMITH_TRACING=true`, `LANGSMITH_API_KEY=...`, `LANGSMITH_PROJECT=delivery-claims-ai`. **Аккаунт проекта — EU-регион**, поэтому обязателен `LANGSMITH_ENDPOINT=https://eu.api.smith.langchain.com`; без него дефолтный US-эндпоинт отдаёт `403 Forbidden` (это несовпадение региона, а не плохой ключ).
- **Важное следствие приватности:** трассы (включая тексты жалоб) уходят в облако LangChain. Для учебного проекта это допустимо, т.к. данные **синтетические**; реальные персональные данные так гонять нельзя — это и есть повод для self-hosted (см. §12), но он вне scope.

### 8.1. Трассировка (tracing)
- Каждый запуск графа = одна **трасса (trace)**; узлы, LLM-вызовы и tool-вызовы — вложенные **run**-ы.
- Логируются: вход/выход каждого узла, промпт и ответ LLM, аргументы и результат tool-вызовов БД, латентность, токены/стоимость.
- К трассе привязываются **метаданные и теги:** `order_id`, `category`, `verdict`, `thread_id`, версия промпта, окружение (`dev`/`staging`).
- `trace_id` кладётся в `State`, чтобы карточка ревью менеджера ссылалась на конкретную трассу.

### 8.2. Обратная связь как ground truth
- Решение менеджера (`approved`/`edited`/`rejected` + правки) отправляется в LangSmith как **feedback** на трассу узла `judge`.
- Ключи фидбэка: `verdict_correct` (bool), `action_correct` (bool), `manager_verdict` (эталонное значение), свободный комментарий.
- Это накапливает размеченный корпус «модель vs. менеджер» без отдельной разметки.

### 8.3. Датасеты
- **`claims_golden`** — курируемый набор эталонных жалоб (см. §3.4 + расширения): вход = текст жалобы + фиксированное состояние БД, эталон = ожидаемый `verdict`/`category`/`order_id`.
- **`claims_from_prod`** — примеры, автоматически собранные из трасс (особенно кейсы, где менеджер правил модель), для дообучения промптов и регрессионных прогонов.

### 8.4. Оффлайн-оценка (evaluators)
Прогон графа по датасету с автоматическими оценщиками:
| Оценщик | Тип | Что проверяет |
|---|---|---|
| `category_exact_match` | детерминированный | совпадение категории с эталоном |
| `order_id_match` | детерминированный | корректность извлечённого ID |
| `verdict_match` | детерминированный | совпадение вердикта с эталоном |
| `reasoning_grounded` | LLM-as-judge | опирается ли аргументация только на факты из БД (нет галлюцинаций) |
| `action_appropriate` | LLM-as-judge | адекватность предложенной компенсации ориентирам §6 |
| `deviation_justified` | LLM-as-judge | если модель отклонилась от ориентира §6 — обоснованно ли (проверка качества самостоятельного суждения) |

Результаты сравниваются между версиями промптов/модели — **регрессионное тестирование** качества перед выкаткой. Поскольку вердикт выносит LLM (вариант B), именно `verdict_match`, `reasoning_grounded` и `deviation_justified` — содержательное ядро оценки: они меряют качество суждения модели, а не работу арифметики.

### 8.5. Онлайн-мониторинг
- Дашборды: распределение вердиктов, доля `insufficient_data`, доля правок менеджера (расхождение модель/человек), латентность, стоимость на жалобу.
- **Алерты:** рост доли расхождений с менеджером, всплеск ошибок tool-вызовов к БД, аномальная латентность.
- Автосемплирование части онлайн-трасс на LLM-as-judge оценку в фоне.

### 8.6. Что демонстрирует учебный проект в связке
LangGraph даёт **управляемый, приостанавливаемый поток** с HITL; LangSmith даёт **видимость каждого шага + петлю улучшения** (трасса → фидбэк менеджера → датасет → оценка → новая версия промпта).

## 9. Human-in-the-loop: контракт интерфейса ревью

Карточка, показываемая менеджеру (данные, не UI-реализация):
- Текст жалобы клиента, канал, срочность.
- Факты из БД: обещанная дата, фактическая дата, статус, дни опоздания.
- Вердикт модели + аргументация.
- Предлагаемое действие (компенсация/отказ/эскалация).
- Ссылка на трассу LangSmith.
- Действия: **Подтвердить** / **Изменить** (редактируемые вердикт и действие) / **Отклонить** (+ комментарий).

Гарантии: ни одна компенсация не применяется без действия менеджера; все правки логируются в фидбэк.

## 12. Риски и допущения (учебные)
- **Галлюцинации фактов** — снижаются приоритетом БД и оценщиком `reasoning_grounded`.
- **Ошибка извлечения order_id** — падение в `insufficient_data`, а не ложный вердикт.
- **Дрейф качества** — ловится мониторингом расхождений модель/менеджер.
- **Structured output через OpenRouter** — у части моделей поддержка JSON-mode слабее; митигируется по §2.3 (JSON-mode + Pydantic-валидация + один retry + безопасный дефолт), а также выбором проверенной модели-судьи в `.env`.
- **Приватность (облачный LangSmith)** — тексты жалоб уходят в облако LangChain (§8.0). Допустимо только потому, что данные синтетические; для реальных ПДн потребуется self-hosted LangSmith — вне scope учебного проекта.
- **Допущение:** данные о заказах достоверны и полны в mock-БД; часовые пояса и рабочие/выходные дни при расчёте `delay_days` в учебной версии игнорируются (кандидат на усложнение).
