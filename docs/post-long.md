# Judging Delivery Complaints with LangGraph and LangSmith

This is a long walk through the design and implementation of delivery-claims-ai, a system that triages customer complaints about late deliveries. It is a slice of a production workflow, adapted and stripped of commercial data so it can be shared, with the architecture and the boundaries left intact. The goal of the write-up is not to sell the project but to explain, honestly and in some depth, how each piece works, why it is shaped the way it is, and what broke along the way. If you are building an agentic workflow that has to touch real data and defer to a human before it acts, most of the decisions here will look familiar, and a few of them might save you an afternoon.

## The problem, stated plainly

An online store receives a stream of complaints. A large share of them are variations on the same theme: my order arrived late, and I am unhappy about it. Handling one of these by hand is tedious but not hard. A support agent opens the order, reads off the date the customer was promised, reads off the date the parcel actually arrived, decides whether the store was genuinely at fault, and if so picks some form of compensation. The work is repetitive, the inputs are structured once you know where to look, and the judgment is bounded. That combination is exactly where a language model earns its keep, and exactly where it can quietly do damage if you let it invent facts.

So the system has a narrow, well defined job. A customer writes free text. The system figures out whether the message is even about a delivery delay, pulls the order identifier out of the prose, looks up the promised and actual delivery dates in a database, and then decides whether the complaint is justified. It attaches a suggested resolution, and it hands the whole thing to a human manager for review before anything is finalized. The manager can approve, edit, or reject. Only then is a decision recorded.

Everything below is built around one sentence that we kept coming back to: code owns the facts, and the model owns the judgment. Almost every design choice in the project falls out of taking that sentence seriously.

## Why the split between facts and judgment matters

There is a tempting shortcut in a system like this. You could hand the model the customer message and the raw database row and ask it to do everything at once: read the dates, compute the delay, decide whether it is justified, and propose compensation. It would often work. It would also, sooner or later, tell a customer that their parcel was eleven days late when it was four, because the model did arithmetic on dates in its head and got it wrong, and nobody noticed because the answer was fluent and confident.

The alternative we chose is to draw a hard line down the middle of the system. On one side is everything that has a single correct answer computable from data: which order this is, what the promised date was, what the actual date was, how many days late that makes it, and what the reference compensation would be according to a fixed ladder. All of that is done by ordinary Python against the database. The model never recomputes any of it. On the other side is the part that genuinely requires judgment: given these established facts and the customer's words, is the complaint justified, what should we offer, and should this be escalated. That is the model's job, and it is the only place the model is trusted to reason.

This is not a compromise that weakens the model's role. It is what makes the model's role meaningful. Because the facts are fixed and correct, the only thing left for the model to be evaluated on is the quality of its judgment, which is the thing we actually care about. If the model had also been responsible for the arithmetic, every evaluation would have been polluted by the question of whether it got the numbers right, and a good verdict built on a wrong number would score as a success. Keeping the arithmetic out of the model is what lets the whole observability and evaluation layer say something true.

## The shape of the workflow

The system is a small state machine. A single object flows through it and accumulates fields as it goes. The stages are classify, extract, enrich, judge, review, and finalize, and there are a couple of deterministic off-ramps for the cases that do not need a verdict from the model.

Classify is the first LLM step. It reads the raw complaint and decides three things: whether the message is about a delivery delay at all, what the sentiment is, and how urgent it seems. If the message is not about a delivery delay, the workflow leaves the main path immediately and routes to an out-of-scope handler that records a polite non-answer. There is no point extracting an order id from a message about changing the color of a shirt.

Extract is the second LLM step, and it does deliberately little. It pulls the order identifier out of the text, in the form the store uses, and it writes a one or two sentence summary of what the customer is actually claiming. If there is no order id in the message, extract returns nothing for that field and the workflow again leaves the main path, this time to an insufficient-data handler that asks the customer for their order number. The model is explicitly told not to guess an order id, because a guessed order id is worse than no order id at all: it would send the rest of the pipeline confidently down the wrong row of the database.

Enrich is the first place code takes over completely. Given an order id, it looks the order up, reads the delivery record, and computes the derived facts. This is where the arithmetic lives. Delivered orders get a delay measured as the difference between the actual delivery date and the promised date. Orders still in transit are measured against a fixed run date: if the promised date has already passed, the parcel is overdue and that is a fact; if it has not, there is simply nothing to judge yet. Lost orders are treated as late but with an undefined delay magnitude. If the order id does not exist in the database, enrich reports that too, and the workflow falls to the same insufficient-data handler. None of this involves the model, and all of it is covered by ordinary unit tests.

Judge is where the model does the work it was kept clean for. It receives the customer's claim summary and the computed facts, and it produces a verdict, a piece of reasoning that cites the facts, and a proposed action. The prompt gives it guidelines rather than rules. In the typical cases the guidelines are obvious and the model follows them: a delivered order that is several days late is usually justified, an order that arrived on time is usually not, an order still within its window is usually a case of insufficient data. But the prompt is explicit that these are orientation, not a lookup table, and that in borderline or disputed situations the model should decide for itself and explain why. The invariants are the non-negotiable part: the facts outrank the customer's words, the model must not recompute any number, and when the data is genuinely insufficient it must say so rather than reach.

Review is the human-in-the-loop step, and it is the reason the whole thing is built on a graph with persistence rather than a straight function call. Finalize is the last step, and it records the outcome and closes the loop back to the observability layer. Both deserve their own sections.

## Getting structured output out of cheap models without trusting them

Every LLM step in this system needs to return structured data, not prose. Classify needs three enum values. Extract needs an order id and a summary. Judge needs a verdict, reasoning, and an action. The usual advice is to reach for the framework's built-in structured-output helper and let it enforce a schema. We did not, and the reason is worth explaining because it is a common source of quiet failure.

The models here are cheap on purpose, because the classification and extraction tasks are not hard and there is no reason to pay for a frontier model to do them. Cheap models vary in how well they support strict JSON or function-calling modes. Some of them will happily ignore a schema constraint and return prose with the JSON buried in it, or return JSON that is almost but not quite valid. If you rely on the framework to enforce the schema and the model does not cooperate, you get an exception deep in the call stack at an awkward moment.

So instead there is a small helper that does three things. It asks the model for a single JSON object and includes the JSON schema of the target type in the prompt so the model knows the shape. It then parses whatever comes back, stripping the code fences and surrounding chatter that models like to add, and validates it against a Pydantic model. If that fails, it does not give up: it feeds the error back to the model and asks once more for a corrected object. Only if the second attempt also fails does it raise, and even then the caller has a safe default ready. The classifier defaults to treating the message as out of scope rather than guessing a category. The judge defaults to insufficient data rather than inventing a verdict. The principle is the same as everywhere else in the system: when in doubt, refuse to fabricate.

This costs a little more code than trusting the framework, and one extra round trip in the rare failure case. In exchange it works reliably across a range of models, and swapping the model behind any node is a one line change in configuration because nothing in the node code assumes a particular provider's structured-output behavior.

## Human-in-the-loop, and why it forces a checkpointer

The manager review is the whole point of the system. No compensation is ever applied automatically. The model prepares a decision, and a human decides whether that decision stands. This sounds like a small feature and it changes the architecture completely.

The naive version would run the graph, stop when it needs the manager, block until the manager responds, and continue. That works in a notebook and falls apart everywhere else, because a real manager does not respond in the same function call. They respond minutes or hours later, possibly after the process that ran the graph has exited, possibly from a different machine. The workflow has to be able to pause, persist everything it knows, survive a restart, and resume from exactly where it left off when the decision finally arrives.

LangGraph handles the pause with an interrupt. Inside the review node, the system builds a card summarizing everything the manager needs to see, the complaint, the computed facts, the model's verdict and reasoning, and the proposed action, and then it interrupts. The graph suspends and writes its entire state to a checkpointer. In this project the checkpointer is a SQLite file, deliberately separate from the orders database so the two never interfere. The state now lives on disk keyed by a thread identifier, and the process is free to exit.

Resuming is a second, independent invocation. It supplies the same thread identifier and the manager's decision, the checkpointer loads the saved state, and the graph continues from the review node as if no time had passed. The command-line interface makes this concrete: submitting a complaint is one command that prints a thread id and the review card and then returns; reviewing is a separate command, run later, that takes the thread id and a decision. We tested this across genuinely separate processes, including the case where the manager edits the verdict rather than approving it, and the edited decision flows through to the final record correctly. That cross-process resume is the real proof that the persistence works; anything that only survives within a single process has not actually solved the problem.

The manager has three options. Approve accepts the model's decision as it stands. Edit lets the manager override the verdict or the proposed action, and those overrides are applied before finalizing. Reject stops the workflow and flags the case for manual handling, without looping back to the model. That last choice was deliberate. A more elaborate system might feed the manager's objection back to the judge and ask it to reconsider, which turns the review into a genuine agentic loop. That is powerful and it is also a good way to build something that argues with itself in circles, so it is kept out of this version and noted as a deliberate extension point rather than built.

## A serialization detail that is easy to get wrong

There is a small but instructive trap in the persistence story. When the graph state is written to the checkpointer, it has to be serialized. The first version of the state carried rich Python objects: enum instances for the category and verdict, and a Pydantic model for the computed facts. It worked in a single process. Then the framework started warning that serializing these custom types was deprecated and would eventually be blocked, because reconstructing arbitrary types from a checkpoint is fragile and a security concern.

The fix was not to fight the serializer but to stop putting rich objects in the state at all. Enums became their string values, and the facts model became a plain dictionary. The rich types still exist and are still used inside the nodes, where they give type safety and validation; they are just converted to primitives at the boundary where the state is stored. This is a good habit in general. The state of a durable workflow is a serialization contract, and the fewer assumptions it makes about custom types, the longer it will keep working across framework versions. Durable persistence was the entire reason the checkpointer existed, so it was worth doing this properly rather than silencing the warning.

## Observability as a first-class concern, not an afterthought

Every run of the graph is traced. The tracing is not decoration; it is the substrate that the evaluation and feedback loops are built on. Each node, each model call, and each database tool call becomes a span with its inputs, outputs, latency, and token cost. When a manager looks at a review card, the card carries the trace identifier so the human decision can be tied back to the exact run that produced the verdict.

The one operational wrinkle worth recording is regional. The tracing backend has separate endpoints for different regions, and an API key issued in one region returns a flat forbidden error against the default endpoint of another. We spent a few minutes convinced the key was bad before testing both endpoints directly and watching one return success and the other refuse. The lesson is mundane and general: when a credential is rejected everywhere by default but accepted somewhere specific, suspect the region or the base URL before you suspect the key. The endpoint is now set explicitly in configuration, and the specification says why, so nobody has to rediscover it.

## Evaluating a system whose core output is a judgment

Because the model owns the judgment and code owns the facts, evaluation can focus on the thing that actually varies. There is a curated golden dataset of complaints, each paired with the classification, order id, and verdict we expect given the fixed database and a pinned run date. Pinning the run date matters: several of the expected verdicts depend on comparing today against a promised date, and if today drifts the expected answers drift with it. Freezing the date makes the dataset reproducible, which is the whole point of a golden dataset.

The evaluators come in two flavors. The deterministic ones check exact matches: did the model pick the right category, extract the right order id, reach the right verdict. These are cheap, they are not subject to opinion, and they are the first line of regression defense. The second flavor uses a separate model as a judge of the judge. One evaluator checks that the reasoning is grounded only in the provided facts and does not smuggle in invented dates or amounts. Another checks that the proposed action is appropriate to the verdict and the facts. A third checks that when the model deviated from the guidelines it gave a sound, fact-based justification for doing so. The evaluating model is deliberately from a different family than the judging model, because using a model to grade its own outputs is a way to launder its own biases into a score.

On the current dataset the deterministic scores are perfect and the grounding and deviation checks pass across the board, with a single action-appropriateness miss that the evaluating model flagged. That single miss is exactly the kind of thing the LLM-as-judge layer exists to surface: not a wrong verdict, but a quibble about the phrasing of a compensation offer. A purely deterministic evaluation would never have caught it, and a human would have had to read every transcript to find it.

## Closing the loop with manager feedback

The last piece turns the human review into training signal without any extra labeling work. When a decision is finalized, the manager's outcome is posted back to the original judged trace as feedback. There are a handful of signals: whether the verdict was accepted without change, whether the action was accepted without change, what the manager's final verdict was, and how the review was resolved. Because these are attached to the trace that produced the verdict, they form a growing, labeled record of where the model and the human agreed and where they did not, gathered as a side effect of people simply doing their jobs.

That record is what makes ongoing improvement possible. The disagreement rate is just one minus the mean of the verdict-accepted signal, and it can be watched over time. The cases where the manager overrode the model are the most valuable examples in the entire system, because they are precisely the situations the current prompt handles poorly, and collecting them into a dataset gives you a targeted regression suite for the next prompt or model version. The offline evaluators can then be run against a candidate version and compared to the current one before anything ships. The monitoring runbook sketches the dashboards and alerts that sit on top of this: verdict distribution, agreement rate, review outcomes, latency and cost, with an alert when agreement drops below the target.

The posting of feedback is best-effort. If the backend is unavailable, the failure is logged and swallowed, because a monitoring hiccup must never break the act of recording a decision the manager has already made. There was also a small API detail here, that feedback attached to a specific run cannot also specify a project, and a forward-compatibility warning that we chose to silence locally rather than paper over incorrectly. These are the kinds of small frictions that do not make it into architecture diagrams but make up most of the actual work.

## What the whole thing adds up to

Read from a distance, the system is unremarkable, and that is the point. A customer message comes in, gets classified and parsed, gets enriched with facts that code computed and the model is not allowed to touch, gets a judgment from a model that is told to reason only over those facts, and waits for a human to agree before anything happens. Every step is traced, the whole thing can pause for a human and resume days later, the judgment is measured against a golden set and against a second model, and the human's decisions flow back as ground truth for the next iteration.

The value of building it this way is not that any single piece is clever. It is that the boundaries are drawn in the right places. Facts and judgment are separated, so evaluation means something. The model is told to refuse rather than fabricate, so its failures are safe. The workflow persists, so the human step is real rather than a demo. And the observability is wired through from the start, so the system can be improved by watching it work rather than by guessing. Those are the properties you want in anything that reasons over real data and then defers to a person, and they are worth more than any individual model choice, which is exactly why every model in the system can be swapped with a single line.
